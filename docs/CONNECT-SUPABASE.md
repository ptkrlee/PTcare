# 로그인·기록 저장 연결하기

현재 소스는 Supabase Auth + PostgreSQL을 사용합니다. Vercel은 홈페이지를 배포하는 역할이고, 대상자 기록은 각 치료사 계정 소유의 Supabase 데이터베이스에 저장됩니다. Vercel만 배포해서는 계정 저장이 가동되지 않습니다.

## 1. Supabase 프로젝트 생성

1. https://supabase.com/dashboard 에 GitHub 계정으로 로그인합니다.
2. New project를 선택합니다. 필요하면 조직을 만들고 프로젝트 이름은 `PTcare` 등으로 정합니다.
3. 데이터베이스 비밀번호는 비밀번호 관리자 등에 보관합니다. 채팅이나 GitHub 코드에 넣지 않습니다.
4. 서비스 운영에 맞는 리전을 선택하고 프로젝트가 준비될 때까지 기다립니다.

## 2. 저장 테이블·접근 제한 설치

1. 프로젝트 왼쪽의 SQL Editor에서 새 쿼리를 엽니다.
2. 이 저장소의 `supabase/schema.sql` **전체 내용**을 붙여넣고 Run을 누릅니다.
3. 성공 메시지를 확인합니다. 이 스크립트는 치료사별 행 접근 제한(RLS), 버전 충돌 방지, 재전송 중복 방지를 설치합니다. 브라우저의 직접 INSERT/UPDATE/DELETE는 허용하지 않고, 소유권을 확인하는 `save_patient_record` 함수를 통해 저장합니다.
4. `schema.sql` 재실행은 기존 임상 기록을 유지하고 승인·한도 테이블과 함수를 설치합니다. 새 권한 기능 설치 후에는 [최초 관리자 지정](ADMIN-SETUP.md)을 반드시 완료하세요. 향후 테이블 구조 변경은 별도의 마이그레이션이 필요합니다. 데이터가 생긴 뒤 테이블을 삭제해서 초기화하지 마세요.

## 3. 이메일 로그인 설정

1. Authentication의 이메일 로그인을 활성화합니다.
2. Authentication → URL Configuration에서 Site URL을 `https://refittherapy.vercel.app`으로 설정합니다.
3. Redirect URLs에도 `https://refittherapy.vercel.app`을 추가합니다. 테스트 배포를 따로 운영하면 그 정확한 주소를 추가합니다.
4. 홈페이지의 “새 계정 만들기”로 치료사 계정을 만들고 확인 메일에서 인증합니다. 운영 정책에 따라 관리자가 Authentication의 사용자 관리에서 계정을 생성할 수도 있습니다. 가입을 제한하고 싶으면 초대 방식으로 운영합니다.
5. 실제 운영에서는 이메일 발송량·발신 설정과 Supabase 요금·백업 정책을 확인합니다. 비밀번호 재설정도 이 이메일 설정을 사용합니다.

## 4. Vercel 환경 변수

Supabase 프로젝트의 Connect/API 설정에서 **Project URL**과 **Publishable key**를 확인합니다. 기존 프로젝트라면 legacy `anon` 공개 키도 지원합니다.

현재 브랜치에는 소유자가 제공한 공개 URL·Publishable key가 기본 연결 정보로 설정되어 있습니다. 같은 프로젝트를 사용하면 Vercel에 값을 다시 입력할 필요가 없습니다. 다른 프로젝트나 환경별 설정을 사용하려면 Vercel Settings → Environment Variables에 다음 두 변수를 등록해 기본값을 덮어씁니다.

| 이름 | 값 |
| --- | --- |
| `VITE_SUPABASE_URL` | 프로젝트의 `https://….supabase.co` URL |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Supabase Publishable key |

이 두 값은 브라우저에서 사용하는 연결 정보입니다. **Secret key, `service_role` 키, 데이터베이스 비밀번호를 VITE_ 변수에 넣으면 안 됩니다.** 기록 접근을 보호하는 것은 위 SQL의 인증·소유권 확인과 RLS입니다. 원본 문서나 환자 기록을 GitHub에 올리지 않습니다.

Production에 적용한 뒤 해당 코드가 있는 브랜치를 배포합니다. 환경 변수 변경만으로 이전 빌드의 값이 바뀌지 않으므로 새로 Deploy/Redeploy해야 합니다. `main`이 현재 운영 브랜치입니다. 개발 기능 브랜치는 DB 연결을 확인한 뒤 main에 통합합니다.

## 5. 실제 서버 연결 검증

첫 검증은 가상 대상자 데이터로 진행합니다.

1. 관리자로 A를 승인한 뒤 치료사 A로 로그인하고 가상 대상자를 등록합니다.
2. BBS 한 항목을 고른 뒤 **서버 저장 완료**를 기다립니다.
3. 다른 휴대폰·브라우저에서 A로 로그인해 동일 응답이 보이는지 확인합니다.
4. 다른 치료사 B로 로그인해 A의 대상자가 보이지 않는지 확인합니다.
5. A에서 페이지를 새로고침하고 마지막 응답이 남아 있는지 확인합니다.
6. 인터넷을 끊은 상태에서 평가 메모를 수정하고 페이지를 떠났다가 돌아와 기기 임시 기록이 복원되는지 확인합니다. 다시 연결한 뒤 서버 저장을 확인합니다.
7. 두 기기에서 같은 대상자를 동시에 수정하면 자동 덮어쓰지 않고 충돌을 표시합니다. “기기 복구본 따로 만들기”는 별도 대상자 저장 한도가 필요합니다. 한도가 부족하면 관리자에게 추가 한도를 요청하세요. 원본 기기 사본은 보존됩니다.

이 검증 전에는 실제 서버의 저장·계정 격리가 확인됐다고 말할 수 없습니다. 자동 브라우저 테스트는 모의 Supabase API를 사용하며, SQL은 임시 PostgreSQL에 모의 인증 역할을 만들어 별도로 검증합니다.

## 저장 동작과 제한

- 대상자 UUID, 회차 UUID로 기록을 분리합니다. 동명이인을 이름만으로 합치지 않습니다.
- 각 입력 이벤트에서 기기 localStorage에 기록하고 약 0.5초 후 서버 동기화를 시작합니다. 페이지 이동 시에도 이미 마지막 입력이 기기에 보존되므로 unload 네트워크 요청의 성공에 의존하지 않습니다.
- 기기 임시 보존과 서버 저장 완료를 구분합니다. 다른 기기에서는 서버에 동기화된 기록만 보입니다.
- 서버가 연결되지 않으면 임시 기록은 해당 기기·브라우저에만 있습니다. 브라우저 데이터 삭제, 시크릿 창 종료, 기기 분실·고장까지 보장하는 백업이 아닙니다. 저장 공간 부족 시 경고하고, 미저장 상태에서 창을 닫으려 하면 경고합니다.
- 기기 임시 사본도 건강정보를 포함합니다. 개인 기기 잠금과 계정별 사용을 유지하세요. 정상 로그아웃은 서버 저장을 확인한 뒤 해당 계정의 임시 사본을 삭제합니다. 동기화 대기·충돌이 있으면 데이터 손실을 막기 위해 로그아웃을 보류합니다.
- 기기에 로그인 세션이 남아 있는 동안에는 브라우저를 다시 열어도 같은 계정으로 복원됩니다. 서버에서 세션을 취소했거나 토큰 갱신이 불가능하면 다시 로그인해야 합니다.
- 기기 임시 기록의 사용자별 키 분리는 서버 접근 제어를 대체하지 않습니다. 타인이 직접 운영체제·브라우저 저장소를 열 수 있는 공용 환경에서는 사용하지 않는 것이 좋습니다.
- 삭제·보관기간 자동 처리, 기관별 공동 담당자 권한 및 의료기록 전자서명은 포함되지 않습니다. 서비스 관리자는 별도 읽기 전용 경로로 전체 서버 기록을 열람하며 이용권 변경은 감사 이력에 남깁니다. 일반 치료사는 본인 소유 기록만 접근합니다.

## 개발 환경의 외부 접속 허용

작업 환경의 네트워크 정책이 package_managers 프리셋만 허용하여 Supabase, refittherapy.vercel.app, ptnote.com 요청이 프록시 터널 HTTP 403으로 차단됐습니다. 이는 Supabase 공개 키가 틀렸다는 판정이 아닙니다. 세 호스트를 기존 프리셋을 유지한 채 환경 설정 초안의 사용자 허용 목록에 저장했습니다. 이 초안은 아직 런타임에 적용·게시된 것으로 간주하지 않습니다. Codex 환경 설정에서 변경을 검토·저장하고 환경을 게시한 뒤 실제 연결 검증을 재개해야 합니다. 이는 Vercel 배포 및 Supabase SQL 실행과 별도의 개발 환경 설정입니다.
